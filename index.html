About

I'm a network and security engineer with around ten months of professional experience and a CCNA behind it. My work sits between the systems that are supposed to be secure and the ones that aren't — configuration, diagnosis, and the unglamorous debugging that keeps infrastructure up when something fails in a way nobody expected.

I run a two-node Proxmox cluster at home with sixteen containers. Not because it counts for anything on paper, but because it's the fastest way to be wrong about infrastructure at scale — and it's where the two host faults below came from. Both looked identical from the outside and had nothing to do with each other.

I keep everything in a structured, cross-linked documentation vault treated as source of truth. It's not an afterthought — it's how I avoid re-applying a fix that already failed once.

Selected work

Two-node Proxmox cluster with a hard-won uptime

Infrastructure · Troubleshooting · Linux

A Proxmox cluster that kept dropping every VM's network at once. Two independent faults, near-identical symptoms:

  1. Intel I219-LM link drops. Firmware bug causing the NIC to lose link intermittently. EEE, ASPM and Wake-on-LAN all triggered it. Disabling those three held for days — then recurred, because a separate hardware-unit hang was being caused by packet offloads. Final fix disables EEE/ASPM/WoL and TSO/GSO/GRO, applied on boot.
  2. i915 crash on GPU passthrough handoff. The host hung when starting or stopping passthrough. Root cause was module load order; fixed by declaring i915 soft-dependent on vfio-pci.

The first fix didn't hold. Diagnosing the second layer underneath is the part that took the real work.
