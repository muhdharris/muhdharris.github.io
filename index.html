About

I'm a network and security engineer with around ten months of professional experience and a CCNA behind it. My work sits between the systems that are supposed to be secure and the ones that aren't — configuration, diagnosis, and the unglamorous debugging that keeps infrastructure up when something fails in a way nobody expected.

I run a two-node Proxmox cluster at home with sixteen containers. Not because it counts for anything on paper, but because it's the fastest way to be wrong about infrastructure at scale — and it's where the two host faults below came from. Both looked identical from the outside and had nothing to do with each other.

I keep everything in a structured, cross-linked documentation vault treated as source of truth. It's not an afterthought — it's how I avoid re-applying a fix that already failed once.

Practised, not just studied

  • Segmentation and isolation — deliberate /24 layout with fixed addressing, containers isolated on their own bridge network
  • DNS control — Pi-hole as network-wide resolver, network hygiene rather than per-device settings
  • Private access without exposing anything — Tailscale over port forwarding
  • Least privilege at the storage layer — NFS exports scoped per share, hardened with all_squash and anonuid
  • Credential hygiene — passwords segregated into one vault, secrets never written into notes
  • Hardware-level fault isolation — a failing NIC taking down every VM, and the driver-level fix

Home infrastructure — two-node Proxmox cluster

Infrastructure · Troubleshooting · Linux

A Proxmox cluster running sixteen containers on hardware I own, and the two hardware faults that took the whole thing offline. Both presented identically from the outside — every VM losing network, host unresponsive — and had nothing to do with each other.

The first fix came from a forum post and held for four days. It wasn't the real cause: a second, unrelated layer was causing a hardware-unit hang. Diagnosing that is the part worth describing.
