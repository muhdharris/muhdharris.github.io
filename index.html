About

My work sits between the systems that are supposed to be secure and the ones that aren't — configuration, diagnosis, and the unglamorous debugging that keeps infrastructure up when something fails in a way nobody expected. Most of it is quiet: a rule set that holds, a switch that keeps passing traffic, a device that gets replaced before anyone notices it was dying.

I built the homelab as a working testbed rather than a collection of labs — it's the fastest way to be wrong about infrastructure at scale, and it's where the two host faults below came from. Both looked identical from the outside and had nothing to do with each other.

Home infrastructure — the testbed that found two faults

Infrastructure · Troubleshooting · Linux

A Proxmox cluster running sixteen containers on hardware I own, and the two hardware faults that took the whole thing offline. Both presented identically from the outside — every VM losing network, host unresponsive — and had nothing to do with each other.

Fault one. Every VM lost network at once and the host stopped responding. A forum post pointed at the onboard Intel I219-LM, where EEE, ASPM and Wake-on-LAN each trigger link drops. Disabling all three held for four days — then it hung twice more with every setting applied. The actual cause was a second layer: packet offloads triggering an e1000e hardware-unit hang. Turning off TSO/GSO/GRO fixed it, and the link has been stable since.

Fault two. The same symptom, a different cause — the host hung whenever a GPU-passthrough VM started or stopped. The i915 driver was claiming the device before VFIO could bind it. Ordering vfio-pci ahead of i915 fixed it, and dropping passthrough entirely in favour of host-iGPU transcoding removed the problem class.

The lesson was that a fix which appears to work is not evidence it works. The first change held for four days and was still wrong. Full write-ups include the approach that silently failed.

Supply chain tracking on Ethereum

Solidity · Dart/Flutter · Testing · Repo

A final-year project I audited and rebuilt, after finding that it proved nothing: the customer transparency screen — whose entire job is proving a supply chain record is trustworthy — was reading a list stored in the browser. The app called four contract functions that had never existed, and presented randomly generated bytes as transaction hashes.

Rebuilt so the contract is the only source of truth. Every read is a chain call, every write returns the hash the chain produced, and the ABI is generated and committed rather than inlined in Dart — which is how the original drifted without anyone noticing.

Fixing it surfaced five further defects, including one where any address could mark another customer's goods as delivered. Sixty-four assertions now cover the flows the app performs, including that those attempts revert.

  • 23 contract functions · 11 events
  • Forward-only shipment status, owner-gated attestation
  • Stock checked and decremented on chain
  • 64 passing assertions

Network scanner and small tools

Python · Flask · Nmap · Ruby

A scheduled host scanning service: point it at a subnet and it walks the range on an interval, logging what answers. The interesting part was making it stoppable — a scheduler that spawns a thread per request will eventually hold several at once, and a scan you cannot interrupt is a scan you cannot shut down when it turns up something you were not expecting. One scheduler thread, an interruptible loop, and a stop endpoint that takes effect immediately.

Alongside it, smaller tools built to understand a protocol rather than to ship: a standalone port scanner, a scraper, and WebRTC connectivity tests. Scan only what you own or are authorised to test.
